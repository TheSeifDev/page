## 09 — أكبر عدو: Scope Creep

الفكرة بتبدأ: *"نعمل تطبيق بسيط."* — بعد شهر: Mobile App + Web Dashboard + AI + IoT + Blockchain + Face Recognition + Payment + Chat + Maps + Social.

والنتيجة: **"مش عارفين نخلص."**

---

## 10 — قسّم المشروع لـ 3 مستويات (MoSCoW)

**مثال PharmaTrack:**

| المستوى | التعريف | في PharmaTrack |
|---|---|---|
| **MUST HAVE** | من غيرها المشروع الأساسي لا يعمل | قراءة حرارة كل 60 ثانية + تخزين offline + مزامنة تلقائية + سجل زمني لكل شحنة + Dashboard للرحلات + تنبيه فوري خارج النطاق |
| **SHOULD HAVE** | مهمة ومفيدة لكن يمكن تأجيلها | تقرير PDF عند التسليم + إشعارات SMS للسائق + رسوم بيانية تاريخية + **النموذج التنبؤي (V1)** |
| **NICE TO HAVE** | إضافات لو بس خلص الـ Core | تطبيق موبايل native + دعم RFID |

> **لاحظ:** الـ AI هنا **SHOULD (V1) مش MUST** — النظام يثبت قيمته بالمراقبة والتنبيه، والتنبؤ طبقة قيمة مضافة. ده بالظبط عكس فخ التضخيم.

## 11 — The Scope Kill List

قبل اعتماد أي Feature اسأل:

> **"لو حذفناها — هل المشروع هيظل يحقق هدفه الأساسي؟"**

لو الإجابة **نعم**: احذفها أو أجّلها.

---

## 12 — عرّف الـ MVP بتاعتك

لازم تعرف تكتب:

> **"لو اضطررنا نسلّم المشروع بكرة — إيه أقل نسخة تثبت إن فكرتنا شغالة؟"**

دي هي الـ **MVP**. والسلم الصحيح:

```diagram
MVP  →  V1  →  V2  →  Future
```

**متبدأش من الـ Future.**

---

## 13 — عقد النطاق (The Scope Contract) [[new]]

أكبر سبب للـ Scope Creep مش التكنولوجيا — **هو إن النطاق عمره ما اتكتب**.

اكتب صفحة واحدة وامضوها كفريق (واتفق عليها مع المشرف):

1. الـ MUST HAVE بالتفصيل (هي دي التعهد)
2. الـ Out-of-Scope صراحةً
3. أي Feature جديدة بتترشح وقت الترم؟ **بتتسجل في Future Work — مش بتدخل الترتيب إلا لو المشرف طالبها**
4. مراجعة العقد عند كل Milestone

> لما الدكتور يقترح Feature جديدة وسط الترم (وده بيحصل كتير): اعرض العقد، وناقش: "ندخلها مكان إيه؟ نأجل إيه؟" — كده أنت بتحمي التسليم من غير ما ترفض طلب المشرف.
